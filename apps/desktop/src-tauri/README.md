# Native desktop host

This independent Cargo workspace contains the Tauri 2 native host. It reads `LAZYBOX_V2_ENDPOINT` supplied by `make desktop`, validates the local origin and bearer, and grants the native HTTP plugin access to that exact Runner RPC origin/path at runtime. The bundled frontend uses a Tauri bootstrap command and native HTTP fetch. No browser/Vite server is needed.

Native console windows carry only validated session/command identities in their navigation. The Runner remains an independent Codefly Go process. `make check-desktop` runs format, unit tests, and clippy. No V1 Rust or daemon implementation is imported; only the existing application icon assets are reused.

Windows use HTML5 file drops in the shared chat component. The native Tauri drag/drop handler is disabled so it does not consume those events. Dropped files use the same browser File API and Runner upload as the picker; no additional filesystem or authentication permissions are granted.

Web panels (WORKSPACES.md, "The Web panel") are child webviews (`src/viewer.rs`, Tauri's `unstable` multiwebview) placed over their panel by the page through the `web_view_*` commands. Capabilities are granted to the app's webviews by label (`host::APP_WEBVIEWS`), never to windows, so a viewer inside a window holds none; a viewer loads only web pages, keeps its own website data, never downloads, and is denied device permissions. Because a window holding a viewer is no longer a single-webview `WebviewWindow`, commands take the calling `Webview` (and `Window`) instead. Links open in the default browser through `open_link` (http, https, mailto only).

Voice (`src/voice.rs`, VOICE.md) is in the host too: the `voice_*` commands run macOS speech recognition on-device (the Speech framework through objc2, fed by an AVAudioEngine tap) and stream partial and final text to the calling webview only, as `voice-event`; `speech_*` read aloud with AVSpeechSynthesizer. The page never holds the microphone; the host opens it for one recognition and closes it at its end. `Info.plist` (merged into the bundle and embedded in dev binaries) carries the microphone and speech-recognition usage descriptions. Viewers cannot call any of it (no capability) and keep their device permissions denied.

Attention notifications go through the host: the webview holds no notification permission, only the `notify_attention`, `set_attention_badge`, `take_attention_destination`, `notification_permission` and `request_notification_permission` commands (`src/attention.rs`). A bundled macOS app posts through `UNUserNotificationCenter` (`src/notifications_macos.rs`): it asks for permission, reports what macOS decided, and returns the error of a refused notification. `tauri-plugin-notification`'s macOS path (deprecated `NSUserNotification`) drops that error, so a refusal looked like success. Elsewhere, and under `tauri dev` (no app bundle), the plugin is used. Working and Dev builds sign their bundle ad hoc, as release builds do, so macOS has a signed identity to allow. Only the main window sends them. A click on a notification opens or focuses the main window and hands it the conversation to show; the destination waits in the host until the window takes it, so a click that reopens a closed main window is not lost. The dock badge is the Inbox count (macOS, and Linux desktops that support it).

"Open in Terminal" goes through the host too (`src/terminal.rs`): `terminal_apps` reports which known terminals are installed (Ghostty, iTerm, WezTerm, Warp, Terminal), and `open_terminal` opens the chosen one (`open -a`, WezTerm's own `start --cwd`, or the person's custom command line through `/bin/sh` with `{dir}` quoted) with `LAZYBOX_RUNNER` naming this app's endpoint file, so `lazybox run` there reaches this Runner. `open_terminal` takes only `{path, app}`: the custom command line is the host's own setting (`terminal.json` in the app's config folder), never the page's. `set_terminal_command` saves a new one only after a native "Allow this terminal command?" confirmation that shows the exact line (the page cannot answer it; clearing it asks nothing), and `terminal_command` reads it back for Settings. A script injected in a window can therefore ask for a known terminal or the command the person allowed, never run a line of its own. A line an earlier version kept in the page's storage is only offered in Settings, to save the same way. Only the app's own main, workspace and chat windows may call these, and the folder must resolve inside a workspace root or worktree the Runner lists at that moment: the host asks the Runner's `ListCollections` with its bearer and never trusts the page for this. A terminal that fails within two seconds reports the first line it wrote on stderr; one still running then (WezTerm, a custom command) keeps running, its stderr in an unnamed temporary file rather than a pipe nobody reads, and is waited for on a thread of its own (`src/children.rs`), so it never meets a closed pipe or stays a zombie. Lazybox is not a terminal emulator; this hands the folder to the person's own terminal. `play_system_sound` (`src/sounds.rs`) plays one macOS alert sound from `/System/Library/Sounds`, by its bare name, with `afplay` at the volume asked, for notification sounds; each `afplay` is waited for the same way.

Every command decides from the window that calls it (its label) or is listed, with the reason, among the few any app page may call (`ANY_APP_WINDOW` in `src/main.rs`, checked by a test over every `#[tauri::command]`): links and media open from the app's own pages only (`host::is_app_window`, never a viewer or a popped-out panel window), feedback, linking the CLI and moving the Runner from Settings (`host::is_workspace_window`), and setting up the service, removing an older Lazybox (`brew uninstall`), the doctor and the Runner log from the setup window. Tauri's app ACL manifest (`tauri_build::Attributes::app_manifest`) is not used: the setup window exists before any Runner capability, viewers must keep holding none, and each command's rule (a window kind, the Runner's workspaces, a confirmation) is finer than a capability can say, so the label checks stay the one place it is decided and tested.

The app's CSP frames only an extension content server's session path (`frame-src http://127.0.0.1:*/x/`, EXTENSIONS.md) and carries `base-uri 'none'` and `form-action 'none'`; `scripts/desktop-dev.mjs` gives the development build the same directives. A Web panel's icon (`src/viewer.rs`) is fetched by the host: for a page on the web, every name is resolved by the host and refused when any address is on this machine or a network it is on (loopback, private, link-local, CGNAT, IPv6 unique-local and link-local, IPv4 in IPv6), and each redirect (at most three) is checked the same way.

Windows have no separate title bar on macOS (`src/title_bar.rs`): every window the host builds (workspace, chat, console, artifact, web, a popped-out panel group, the setup window) has an overlay title bar with a hidden title (still set, for Mission Control, the Window menu and accessibility) and the close, minimize and zoom buttons placed in the page's header, centred in its height. The buttons' size and spacing are measured once from a window AppKit lays out but never shows, since they differ between macOS versions. The page (`packages/surfaces/src/title-bar.ts`) asks `title_bar` for the room to leave them, marks its header's empty parts with `data-window-drag-region` and calls `title_bar_drag` and `title_bar_double_click` (which follows "Double-click a window's title bar to" in System Settings, where Tauri's own drag regions always maximize); the host sends `title-bar-full-screen` when a window enters or leaves full screen, where the buttons and their room go away. A popped-out panel window's presses arrive from the window that draws it and act on the popped-out window in front. Elsewhere `title_bar` answers nothing and the system's title bar stays.
