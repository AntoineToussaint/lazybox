# Claude SDK worker

`main.ts` hosts the pinned supported Agent SDK, streaming input, native permission/question callbacks, images, interruption, stopping one sub-agent (`stop_agent`), switching the model of the following turns (`model`, the SDK's `setModel`), and managed command tools. `browser.ts` gives coding agents the agent browser's thirteen `browser_*` tools on the `lazybox_browser` MCP server when the Runner offers it (`open` with `browser: true`), each routed to the Runner tool of the same name, screenshots returned as images, allowed without a per-call prompt because the Runner asks per site ([BROWSER.md](../../../BROWSER.md)). `catalog.ts` reports the agent's own slash commands and models once per change as `command_catalog` (from the initialize response, each turn's `init`, and `commands_changed`); a command is run by sending `/name args` as the message. `status.ts` reports a sign-in Claude cannot use or renew as `auth_required`, by Claude Code's typed cause (`api_error`) where the coarse `error` no longer says so. A macOS Keychain that refused a renewed login (since Claude Code 2.1.329 `invalid_request` with `api_error: oauth_refresh_store_refused`) is not one: the stored login is intact, so it is a provider error whose text is that cause (the client asks to unlock the Keychain and send again), with account state `unknown`, which neither marks the account, switches subscription nor leaves the profile out of reviews. It reports a compaction as `compacted` and a local command's printed output as the agent's text. Sub-agent prose is forwarded (`forwardSubagentText`) and coding agents get progress summaries (`agentProgressSummaries`); `status.ts` attributes a sub-agent's text and tools by `parent_tool_use_id` and adds its brief, usage, summary and outcome to `agent_status` data. A run Claude forks without a task (a Skill with `context: fork`) is reported as a sub-agent from its first event to its call's result, and when the main turn ends anything it blocked on (a foreground task, a forked run) that never reported an end is reported `unknown` with reason `turn_ended`; background tasks are left running. `settings.ts` gives only the Help assistant the `lazybox_settings` MCP server: reading Lazybox's settings needs no approval, and an update runs only for an input the user allowed on its approval card. `permissions.ts` turns Claude's asks into approval cards with their "always allow" choices: one for the workspace is Claude's own rule in `.claude/settings.local.json`; one for the conversation is a grant the worker enforces and reports (`permission_grant`), which the Runner keeps with the conversation, opens every later worker with (`open` `grants`) and takes back on request (`revoke`). Bash, Monitor, PowerShell and the managed command tool run commands (`COMMAND_TOOL_NAMES`): in Lazybox's "ask" permission each has a tool-wide `ask` rule (`options.ts`), so a saved allow rule or Claude's read-only auto-allow never runs one unasked. Without Claude's suggestions (since SDK 0.3.325 Claude sends them for Bash and Monitor only when the saved rule would allow that command) they offer the exact command and its plain prefix (PowerShell: the exact command only), never a grant for every request. A tool-wide grant for one of them is not restored: the worker reports each grant it was opened with and does not hold (`permission_grant_dropped`), and the Runner stops keeping and listing it. `settings-effect.ts` watches for Claude's `settings_not_in_effect` warning (SDK 0.3.330): a session whose approvals rest on the worker's `ask` rules ("ask", the help assistant) ends with `sdk_error` and Claude's list of what did not load only when Claude rejected Lazybox's own permission settings (its inline settings did not load, or an entry under `permissions` was skipped) or did not say which settings it rejected; when only the person's settings files or Lazybox's other settings were rejected, and in every other session, the worker reports the warning, naming them, as a `provider_notice` (one line in the conversation that never faults it) and the agent goes on. `main.test.ts` runs the worker over its pipe against a stand-in Claude Code to pin that wiring and the grant-drop report. `steer.ts` hands a message to the running turn (`steer`, priority `next`): Claude Code folds it in between two steps, as its own terminal does; the worker refuses a steer while no turn runs, and the Runner keeps that message for its own turn. `interrupt.ts` applies an interrupt to the turn it was asked for and no other: one that failed, or arrived after its turn ended, leaves the next turn's failures as they are. When the SDK stream ends (`stream.ts`) the worker reports why (`provider_process_exit`, or `sdk_error`) and exits once that line is written, so the Runner sees the agent process end instead of a worker that accepts messages nothing reads. `wire.ts` reads the Runner's lines, at most 64 MiB each (`LINE_LIMIT`, equal to the Runner's `claude.WorkerLineBytes`, which takes the largest message the Runner accepts with its attachments and images as base64): a request longer than that is answered with an error under its own id, a reply to a tool call that long fails that call, and a line that is not a JSON object (`null`, text) is set aside and said on stderr; none of them ends the worker. Go owns queueing, journals, account context, and command execution. Build with `make build-worker`; see `RUNNING.md` for limits.
