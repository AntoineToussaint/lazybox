# Can Lazybox tell whether the requested work succeeded?

Source audit at Lazybox revision 78ef3d11, November 22, 2026. The user needs an answer at the end of an ordinary conversation, on a Mission board, and when reading a saved deliverable.

## Verdict on the catalog example

**Required deliverable: authenticated catalog API. Outcome: incomplete, blocked at service generation.** A storage milestone passed. The generator failed. The service-level acceptance tests have no result. Human acceptance is a separate decision.

| Question | Observed result | What the product should show |
|---|---|---|
| Did the catalog schema work in isolation? | The corrected PostgreSQL smoke test exited 0. Rename, duplicate suppression, cross-tenant read isolation and down migration were exercised. | Passed · storage only. Label the evidence as a direct database check. |
| Were there failed attempts? | Service generation exited 1 on container recovery ownership. An earlier database run exited 3 when the restricted role attempted rollback. A subsequent run used the migration owner successfully. | Generator failure open. Earlier database failure retained as resolved by the corrected run. |
| Was the authenticated service delivered? | Module registered with an empty services list. No service process or authenticated RPC was exercised. | Delivery blocked. API replay, cross-tenant RPC denial and restart checks unrun. |
| Was the first apparent smoke success sufficient? | One command exited 0 after applying and reverting DDL, but its stdin assertions did not execute. | Successful process with insufficient coverage. Require evidence that the named assertions ran. |

## Recommended ownership and behavior

**The definition of done describes the required behavior. The Runner owns observed outcomes. Missions aggregate them, and artifacts publish a versioned snapshot.** Use one projection across all surfaces, including conversations without a Mission.

1. Give each required criterion a stable ID scoped to a contract version. Record expected behavior, evidence method, requirement level and target. A generated service, an authenticated API response and restart durability are distinct criteria. The person can approve a scope revision with a recorded reason.
2. Append an observation with criterion ID, contract digest, attempt, checked candidate, source, command/check ID, outcome and output reference. Record setup failure separately from an assertion failure. A declared success without observed evidence remains unverified. For uncommitted changes record a snapshot identity or mark revision binding uncertain.
3. Keep raw failures permanently in the attempt history subject to existing retention. Resolve an open failure only with valid evidence for the same criterion on the applicable candidate, or an explicit scope decision. Preserve both attempt references. Mark old proof stale when inputs change. If command output expires, retain the verdict and show that the output is unavailable.
4. Derive delivery success only when every required criterion has current passing evidence. Show failed for a failed required behavior, blocked when a prerequisite prevents checking it, and incomplete when required checks remain unrun. Display counts and each reason when these coexist. Track cancellation and human acceptance separately. An explicit waiver records who accepted which gap.
5. Put the verdict and first unresolved required issue on the conversation completion card, Mission task, acceptance inbox, CLI JSON and published outcome report. Show resolved failures in history. Use scoped references and existing access controls for logs; a portable report should not copy raw private output.

## Implementation order and definitions of done

| Slice | Deliverable and exit test |
|---|---|
| 1. Make existing history visible | In the command and Mission surfaces distinguish latest run, historical failures and outstanding delivery verdict. Replay generator failure then unrelated SQL success. Both remain discoverable from the collapsed summary. Without criterion attribution label the earlier failure’s resolution unknown. |
| 2. Bind evidence to criteria | Add a versioned contract format and durable Runner observation events with idempotent recording. Replaying or restarting does not duplicate an observation. Unknown, piped, missing-output and no-assertions cases never satisfy a required behavior solely from process exit. Existing specs remain readable. |
| 3. Unify completion and acceptance | Use the same reducer for ordinary conversation, Mission task, CLI and inbox. Test all-pass, mixed results, infra blocker, same-check repair, stale revision, waiver and concurrent attempts. Accepting a task with an outstanding blocker preserves the blocker and records the decision. |
| 4. Publish reproducible outcomes | Add a structured outcome artifact or a new versioned report schema referencing the immutable snapshot. Inspect an old report after a later fix and see the original failure. A newly published report links the repair and retains the earlier attempt. Verify authorized versus unauthorized log access. |
| 5. Prove the user journey | Run the catalog sequence from a conversation with and without a Mission. Verify desktop, CLI, restart and artifact export agree. Bind the eventual authenticated API check to the exact service candidate. The delivery verdict changes to passed only after all required API checks pass. |

## Verification and limits

The existing Go suites for internal/work and internal/runner/artifacts passed. Their coverage includes golden Mission histories and pinned-review handling. The catalog sequence above uses observed command results from this conversation. The proposed mixed-outcome acceptance suite has not been implemented. This audit inspected UI code without a live UI replay. The Runner restricts listing personal Missions from the agent endpoint, so this conversation's Mission assignment could not be established. No product behavior was changed.
